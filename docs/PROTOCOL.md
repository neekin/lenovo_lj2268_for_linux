# 协议与验证边界

输入为 CUPS raster，默认 A4、600dpi、8 位灰度；阈值化后形成 1bpp 图像，横向填充到 512 点整数倍，再通过 JBIG-KIT 压缩并封装为 LHPL。

作业结构：PJL 作业控制 → `ESC LH @sj` → 每页 `ESC LH @sp`＋JBIG＋`ESC LH @ep` → PJL EOJ。

- `@sj`、`@sp`、`@ep` 都是 6 字节命令加 58 字节载荷，完整帧 64 字节。
- 帧末字节是前面 63 字节的异或校验。
- `@sp` 载荷偏移 `0x0e` 和 `0x12` 的压缩长度为小端 **32 位**，不是 16 位。
- JBIG 使用带高 128、`JBG_LRLTWO | JBG_SDRST`、order/mx/my 均为 0。
- 8 位灰度默认使用 Pillow 查表、位打包；库由安装环境原生编译。

当时使用同一 raster 对比官方 macOS filter 和 Linux 输出，确认页头及 JBIG 数据一致，修正页结束帧后实际出纸。另有压缩长度超过 65535 的样本用于验证 32 位长度字段。相关记录见 `evidence/`。

`@ep` 载荷中的部分不透明字段保留了正常工作的参考值，其全部语义尚未恢复。不能宣称完成 Windows 驱动的所有功能。PPD 保留了现有设备配置中的选项，filter 并未完整实现其中所有厂商扩展：特别是不据此宣称自动双面、特殊介质或额外分辨率已验证。

LJ2268 单页和用户实际中英文/iPhone 作业已实机确认。解析器支持两种历史 raster 多页排列；软件自检验证帧数，但不等于所有应用程序和纸张的多页实机验证。

## CI 验证

`.github/workflows/validate.yml` 使用 x86_64 与 ARM64 原生 Linux runner：

1. 安装依赖、原生编译、安装驱动。
2. 测试 ctypes ABI、JBIG 输出尺寸、灰度位打包、双页帧结构和校验。
3. 检查 PPD，并通过真实 CUPS 过滤器将 PDF 转 raster，再转换为 LHPL。
4. 建立指向本机无打印设备地址的测试队列，检查同名保护及更新流程；不提交打印任务。
5. 构建 Docker 镜像，验证运行镜像内的库可加载。
6. 保存编译产物及日志到 workflow artifacts。

CI 结果必须查看对应 commit 的实际运行状态，不能仅凭工作流文件存在就写“已通过”。
